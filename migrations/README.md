# 数据库迁移与查询规范

`migrations/` 同时存放两类 PostgreSQL 源文件：根目录下的 Goose 数据库迁移，以及 `queries/` 下供 sqlc 生成仓储代码的查询。这里的文件会被编译、嵌入二进制并在部署时执行，任何改动都必须同时考虑数据库升级、回滚、sqlc 生成和租户数据隔离。

## 目录与工具链

- `000NN_name.sql` 是按顺序执行的 Goose 迁移。迁移文件通过 `migrations/embed.go` 嵌入程序，不能依赖运行时工作目录。
- `queries/*.sql` 是 sqlc 查询源，配置见仓库根目录的 `sqlc.yaml`。查询名和返回形状会生成 Go API，修改它们等同于修改仓储接口。
- 迁移使用 PostgreSQL 语法；不要为了“可移植”而牺牲 PostgreSQL 的约束、JSONB、锁或索引语义。

## 新增迁移

1. 使用下一个五位数字序号和小写蛇形名称，例如 `00005_add_asset_index.sql`。序号一旦发布不可重排、复用或改名。
2. 每个文件必须包含成对的 `-- +goose Up` 与 `-- +goose Down` 标记，顺序固定为 Up 在前、Down 在后。段落前可以写自然的中文目的描述，不要使用分类标签。
3. 已经在任何环境执行过的迁移视为不可变更。修复问题必须新增迁移，不能编辑旧文件“补丁式”修改。
4. Up 和 Down 尽量保持可逆：新增表、列、索引、约束时在 Down 中按依赖反向删除；删除或破坏性变更前必须先确认数据迁移策略。
5. 需要跨多条语句保持原子性时依赖 Goose 默认事务；创建函数、触发器等包含内部分号的语句才使用 `-- +goose StatementBegin` / `-- +goose StatementEnd`，并在注释中说明原因。
6. 对可能重复执行的对象使用 `IF EXISTS` / `IF NOT EXISTS` 需要谨慎：它不能替代正确的版本控制，也不能静默掩盖对象定义不一致。
7. 新增或删除列、约束、索引时检查现有查询、外键依赖和生产数据量。大表索引、回填和锁表操作必须在注释中写明风险及上线顺序。

## SQL 格式

- 文件统一使用 UTF-8、LF 换行；关键字、类型和函数使用大写，表名、列名和 sqlc 参数使用小写蛇形命名。
- 使用两个空格缩进；表定义和 `INSERT`/`UPDATE` 的列清单一列一行；约束、索引和 `COMMENT` 作为独立语句。
- 顶层对象之间留一个空行；`WHERE`、`JOIN`、`ORDER BY`、`SET` 和 `VALUES` 的条件或字段逐行排列，布尔连接词放在续行开头。
- 单行尽量不超过 120 个字符。长的 `CHECK`、`IN` 列表、JSON 字面量和函数调用应拆成多行，不能为了短而改变字符串内容。
- 每条 SQL 语句以分号结尾。不要把多个无关对象压在同一行，也不要提交编辑器生成的尾随空格。
- 迁移中的 `COMMENT ON` 是数据库元数据，内容应解释业务含义、取值范围、时区、敏感性和生命周期；不要写实现过程或临时工单号。

## 注释与数据库元数据

- 每个表的 `CREATE TABLE` 结束后，紧接着写 `COMMENT ON TABLE` 和该表全部 `COMMENT ON COLUMN`；列注释顺序与字段定义顺序一致，便于一起审阅。
- 每个持久化列必须有且只有一条 `COMMENT ON COLUMN table_name.column_name IS '...'`，内容使用中文，说明业务含义、取值范围、时区、敏感性或生命周期。
- 迁移的 Up/Down 段前写自然的中文目的描述；高风险操作补充锁、回填、兼容窗口和回滚限制。不要添加“说明”“提示”等分类前缀或元话术标签。
- 查询描述应放在对应 `-- name: QueryName :one|:many|:exec|:execrows` 标记之前，使用自然中文表述读写对象、租户边界、排序或锁语义。
- 不在注释中记录真实凭据、令牌、个人数据或生产样本。SQL 中的 JSON 示例也只能使用脱敏占位值。

## sqlc 查询约束

- `-- name:` 标记必须唯一，结果类型后缀必须准确：`:one`、`:many`、`:exec` 或 `:execrows`。不要改名来掩盖兼容性变化。
- 所有租户数据查询必须显式携带 `tenant_id` 条件；跨租户平台查询要在中文注释中明确说明，并通过 `LEFT JOIN` 等方式保留平台级记录的语义。
- 写入语句优先使用 `RETURNING` 返回持久化后的完整事实；并发更新使用 revision、状态条件或行锁，不能依赖应用层先读后写。
- 分页查询必须有稳定、唯一可复现的 `ORDER BY`，通常以业务排序列加 UUID 作为末列，并配套同谓词的 `Count` 查询。
- 不在查询中拼接用户输入；使用 `sqlc.arg` / `sqlc.narg`，并在必要处显式转换类型。敏感字段只返回元数据或加密值，绝不返回明文秘密。
- 保持 `SELECT` 列表和调用方使用的返回结构稳定。确实需要整行返回时可以使用 `SELECT *`，否则列出显式字段以避免无意的 schema 变化。
- 需要“领取一条待处理记录”时使用事务内 `FOR UPDATE SKIP LOCKED`，并同时设计租约过期、幂等和旧 worker 隔离条件。

## 提交前检查

在仓库根目录执行：

```bash
go tool sqlc vet
go generate ./...
git diff --check
```

如果修改了 schema 或查询，必须审阅并提交对应的 `internal/generated/repository` 生成差异；没有源文件变更时，生成结果应保持干净。再检查迁移顺序、Up/Down 对称性、表列注释、租户谓词和超长行。涉及真实 PostgreSQL 行为的改动应在与生产版本一致的 PostgreSQL 16+ 环境执行升级与回滚演练；没有数据库时至少运行 sqlc vet，并在变更说明中记录未执行的验证。

## Agent 工作流

Agent 开始写迁移前先阅读本文件、最后一个迁移和相关查询；先列出依赖关系，再编辑 SQL。完成后重新读取改动文件，确认 Goose 标记、sqlc 标记、分号、表列注释和格式均完整，最后运行上面的检查。遇到破坏性变更、无法安全回滚或不确定的租户边界时，应停止编码并请求明确的产品或数据库决策。
